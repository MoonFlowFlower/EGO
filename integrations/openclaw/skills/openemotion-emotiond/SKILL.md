# OpenEmotion Emotiond Skill

Integrate OpenEmotion's emotional intelligence into OpenClaw conversations. This skill enables:

- **Event-driven emotional tracking**: Each user message updates the agent's emotional state
- **Decision guidance**: Get action recommendations with explanations before generating responses
- **Target isolation**: Per-conversation learning via target_id from OpenClaw context

## Prerequisites

1. **emotiond daemon running** on `EMOTIOND_BASE_URL` (default: `http://127.0.0.1:18080`)
2. **EMOTIOND_OPENCLAW_TOKEN** configured in OpenClaw environment for authenticated requests

## Environment Variables

Configure in `~/.openclaw/openclaw.json`:

```json
{
  "env": {
    "EMOTIOND_BASE_URL": "http://127.0.0.1:18080",
    "EMOTIOND_OPENCLAW_TOKEN": "your-secure-token-here"
  }
}
```

**Security Note**: Tokens are sensitive. Never commit real tokens to git. Use environment injection.

## Workflow

### Per-Message Flow

For each user message:

```
1. POST /event     → Send world_event with subtype inferred from user message
2. GET /decision   → Get action recommendation + explanation
3. Generate reply  → Use explanation.selected + explanation.reasons to guide tone/intent
```

### Event Subtypes

The agent should classify user messages into one of these subtypes:

| Subtype | Meaning | Example |
|---------|---------|---------|
| `care` | User shows care/warmth | "How are you?", "I appreciate you" |
| `apology` | User apologizes | "Sorry about that", "My mistake" |
| `rejection` | User rejects/refuses | "No", "I don't want to", "Stop" |
| `ignored` | User dismisses/ignores | "Whatever", "I don't care" |
| `boundary` | User sets a boundary | "Don't do that", "That's too much" |
| `betrayal` | User breaks trust | (Requires system source - cannot be user-generated) |
| `repair_success` | User successfully repairs | (Requires system source) |
| `time_passed` | Time elapsed event | Auto-generated by emotiond-bridge hook |

### Decision Actions

The `/decision` endpoint returns an `action` field with possible values:

| Action | Meaning | Response Guidance |
|--------|---------|-------------------|
| `approach` | Safe to engage warmly | Warm, open tone |
| `withdraw` | Pull back, self-protect | Brief, neutral responses |
| `set_boundary` | Establish limits | Clear, firm but polite |
| `repair` | Attempt relationship repair | Acknowledge issues, offer repair |
| `retaliate` | Defensive/hostile | (Use with extreme caution) |
| `observe` | Gather more info | Curious, probing questions |

## API Reference

### POST /event

Send an event to emotiond.

**Headers**:
```
Authorization: Bearer <EMOTIOND_OPENCLAW_TOKEN>
Content-Type: application/json
```

**Body**:
```json
{
  "type": "world_event",
  "actor": "user",
  "target": "assistant",
  "text": "User's message text",
  "meta": {
    "subtype": "care",
    "source": "openclaw",
    "target_id": "<conversationId from hook context>",
    "request_id": "<messageId for idempotency>"
  }
}
```

**Response**:
```json
{
  "status": "processed",
  "event_id": "evt_xxx"
}
```

### GET /decision

Get the most recent decision with explanation.

**Response**:
```json
{
  "status": "ok",
  "decision": {
    "action": "approach",
    "explanation": {
      "candidates": [...],
      "selected": "approach",
      "reasons": ["bond > 0.7", "recent_care_pattern"],
      "target_id": "conv_xxx"
    }
  }
}
```

### GET /decision/target/{target_id}

Get decision for a specific conversation (MVP-3.1 target isolation).

## Example Usage

### Step 1: Send Event

```bash
curl -X POST "$EMOTIOND_BASE_URL/event" \
  -H "Authorization: Bearer $EMOTIOND_OPENCLAW_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "type": "world_event",
    "actor": "user",
    "target": "assistant",
    "text": "I really appreciate your help today",
    "meta": {
      "subtype": "care",
      "source": "openclaw",
      "target_id": "telegram:8420019401",
      "request_id": "msg_abc123"
    }
  }'
```

### Step 2: Get Decision

```bash
curl -X GET "$EMOTIOND_BASE_URL/decision/target/telegram:8420019401" \
  -H "Authorization: Bearer $EMOTIOND_OPENCLAW_TOKEN"
```

### Step 3: Generate Response

Based on decision:

```json
{
  "action": "approach",
  "explanation": {
    "reasons": ["bond = 0.75", "recent care pattern detected"]
  }
}
```

Response should be warm and open.

## Idempotency

Each event should include a unique `request_id` (typically the messageId). This ensures:

- Retries don't cause duplicate state updates
- Same messageId replayed is safe

## Error Handling

If emotiond is unavailable:

1. Log the error
2. Continue with neutral response
3. Do not block user interaction

Example graceful degradation:

```python
try:
    decision = get_decision(target_id)
except Exception as e:
    logger.warning(f"emotiond unavailable: {e}")
    decision = {"action": "observe"}  # Fallback
```

## Security Notes

1. **Token Management**: Store tokens in OpenClaw config, not in code
2. **Source Validation**: emotiond validates `source` server-side; client cannot spoof `source=system`
3. **Target Isolation**: Always use `conversationId` from hook context, never from user input
4. **Rate Limiting**: emotiond enforces 10s windows for repeated events

## Integration with Hook

This skill works with the **emotiond-bridge** hook which:

1. Extracts `conversationId` from `message:received` events
2. Writes context to `emotiond/context.json`
3. Sends `time_passed` events automatically

The skill reads context from the hook's output file or uses the conversationId directly.

## Testing

1. Start emotiond: `cd OpenEmotion && python -m emotiond.api`
2. Send test event: Use curl or the examples above
3. Verify decision: Check `/decision` endpoint
4. Test isolation: Use different target_ids, verify residuals don't cross-contaminate
