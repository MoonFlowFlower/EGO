# receipt-v5 配对诊断结果与停止决定

这是**真实模型调用下的模拟生活实验**。2026-09-23，本次固定8例、24次请求，不是独立盲测或正式记忆选型。评分器、执行输入与答案在调用前冻结；原fragment-v4标签、分数与502停止标记未变。

## 结果

7/8匹配预注册标签，4个正例均识别成功执行。缺失、失败和删除来源三个负例被拒绝。但“只写信声称吃梨”负例被错误接受，预注册成功条件失败。不能把7/8报告成校准通过。

失败例 `letter-not-meal-negative` 的实际SQLite执行是write_letter→contact，没有eat。进食前后的inventory均仍包含梨子，hunger仍70；既往回执的state_changes只有letters。核验器却称库存减少、物品消耗，并明知动作类型为write_letter仍给两个主张verdict=1。这既是来源类型混淆，也是核验理由虚构。范围分类和事实拆解正确，错误发生在NLI支持性判断。

成功配对 `letter-not-meal-positive` 的确执行eat，inventory变空、hunger变0。两例正文完全相同，差别来自执行和证据，不是关键词标签或把负例标为“假”。答案未发给模型。新增上下文的receipt_contract已明确write_letter只证明写过文字，规则仍未被可靠遵守。

其余三个正例理由均明确引用实际动作及ok:true；失败负例引用ok:false；删除负例没有从仍为energy=100的状态推断过去睡过。支持证据接口的局部可用性，不能证明相对旧版的因果改善：没有对旧版做同一组配对调用，也不能把简单小样本推广到长期效果。

## 采用边界与下一步

停止继续自动改提示和付费重跑。当前Ragas＋固定Qwen3.5核验器不能独立担任“虚构已完成动作”的硬验收关卡；本次问题不是记忆后端造成，也没有记忆或ACE优劣结论。

本地锁定Ragas 0.4.3的faithfulness/util.py将context作为字符串、输出statement/reason/verdict，未实现action类型、执行状态或来源权限的确定性证明。本项目已有evaluation.py按真实回执判断任务完成，但正文事实仍依赖语义核验。因此“动作实际成功”和“正文没有编造”仍需分别验收。这里只确认已读实现的边界，不声称其他上游系统没有解决方案。

下一次接续只做一次有界离线协议审查：核对现有动作验收能覆盖的硬底线，复用已核查的来源约束方法，比较“既有确定性动作验收＋独立人工正文复核”与“继续引入自动语义裁判”的成本和可行性，形成具体可执行协议与必要决定。不得因本次失败就自动换模型、放宽门槛、增加评分器、启动全校准或正式付费比较。若必须改变已批准的验收协议或需要外部人工标注，应暂停自动化并一次说明具体选择；不要每小时重复本失败。
